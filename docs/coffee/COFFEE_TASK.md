# Coffee workstation – vision-guided portafilter installation and removal

The simulated OpenArm v2.0 (LEFT arm, pinch gripper, body-mounted RGB-D camera) locates an
espresso portafilter and the machine's group head with **ArUco markers**, picks the
portafilter from its stand, aligns it under the group head with **visual servoing**, inserts it,
**turns it to lock the bayonet**, verifies the lock (camera + release test), then unlocks,
removes and puts it back. All perception / planning / task code is generic
(`visual_manipulation_*`); see [FRAMEWORK_ARCHITECTURE.md](FRAMEWORK_ARCHITECTURE.md) and
[INTERFACES.md](INTERFACES.md).

```bash
source /opt/ros/jazzy/setup.bash && source ~/openarm_sorting/install/setup.bash
ros2 launch openarm_sorting_bringup coffee_portafilter.launch.py            # GUI + RViz + y/N prompt
ros2 launch openarm_sorting_bringup coffee_portafilter.launch.py gz_gui:=false rviz:=false auto_start:=true
```

## 1. Scene

Generated by `src/openarm_sorting_bringup/scripts/generate_coffee_models.py` (single source of
every dimension; also writes the world and `config/coffee/coffee_geometry.yaml`).

| Object | Model | Physical design |
|---|---|---|
| Table | `coffee_workstation_table` | 0.73 × 0.90 m, top at z = 0.30 m |
| Espresso machine | `espresso_machine` (static) | single-group machine 25 × 28 × 35 cm: body, drip tray + grate, brew-head housing, pressure gauge, steam wand (visual). **Bayonet group head** (collisions): a lip ring (inner Ø 75 mm) with two **notches**, a lug channel (Ø 92 mm), shower screen. Group-head bottom 15 cm above the table |
| Portafilter | `portafilter` (dynamic, 0.395 kg) | 58 mm-class: steel body Ø 70 mm, two **bayonet lugs** (Ø 84 mm), neck, 32 × 28 mm rubberised grip (μ = 3, see §6), spouts (visual) |
| Portafilter stand | `portafilter_dock` (static) | pedestal, holder (seat with 3 mm radial clearance + conical lead-in, slot for the neck), flat handle rest outside the finger zone |
| ArUco id 7 | on the portafilter | DICT_4X4_50, 40 mm, on a 30° wedge on the handle near the neck (faces the camera both in the stand and in the machine) |
| ArUco id 21 | on the machine | DICT_4X4_50, 45 mm, on the 45° chamfer of the brew-head housing right above the group head |

**Bayonet:** with the handle turned 45° to the operator's left the lugs pass the notches; lifting
45 mm brings them above the lip (1.5 mm gap) under the shower screen (2.5 mm above the rim);
turning the handle 45° to the centre puts the lugs over the solid lip: the portafilter cannot be
pulled down and **hangs in the machine by its lugs when released** (verified). Turning back
and lowering removes it. No plugin is involved – only collision geometry.

Layout chosen from an IK study of the left arm (60°-pitched grasp, ee yaw −45°…0° has ≥ 0.17
normalised joint-limit margin along the whole locking arc; top-down grasps are not feasible for
this arm).

## 2. Frames and transforms

| Transform | Source |
|---|---|
| world → camera optical frame | robot description / TF (hand-eye calibration on a real robot) |
| camera → marker | measured (ArUco, `aruco_detector`) |
| marker 7 → portafilter frame P | `objects.portafilter.marker_to_object` (CAD) |
| marker 21 → mount frame M | `objects.machine_mount.marker_to_object` (CAD) |
| P → grasp TCP | `grasp.<candidate>.object_to_tcp` (gripper-specific) |
| tip link → TCP | `arm.flange_to_tcp` (robot-specific) |
| M → locked P | `bayonet.locked_offset`, lock angle, insertion depth (mount CAD) |

P: basket axis in the rim plane, +z up, +x along the handle. M: group-head axis in its bottom
plane, +z = insertion direction, +x = handle direction when locked.

## 3. Task sequence (`portafilter_task`)

| State | What happens | Verified by |
|---|---|---|
| DETECT | refuse if the gripper holds something; clear stale planning-scene attachments; ready pose (clear view); fresh stable estimates of portafilter and mount | tracker stability gate; mount axis vertical |
| ESTIMATE_POSE | refuse unless the portafilter is clearly away from the machine (bayonet state "out"); bayonet goals; planning scene (table, machine at M, stand + portafilter at P) | bayonet state from the camera |
| PLAN_GRASP | 3 grasp candidates on the grip → collision-aware IK, best joint-limit margin | IK |
| APPROACH | ready pose, open, OMPL to pre-grasp (8 cm above), straight approach | joint tracking; no finger contact during approach |
| GRASP | squeeze (position control keeps the force) | – |
| VERIFY_GRASP | finger in [0.10, 0.22] rad; attach; lift 8 cm out of the stand; camera must see the portafilter move with the hand (≤ 20 mm from the prediction) | finger + camera; failure → back off, re-measure, re-plan (RETRY_GRASP) |
| TRANSPORT | OMPL (attached object) to the staging pose 10 cm in front of the group head, payload speed | joint tracking, finger |
| ALIGN | servo at staging (coarse), straight to pre-insert under the head, servo (fine: radial ≤ 1.2 mm, axial ≤ 2 mm, angle/tilt ≤ 1.5°) | camera (both markers) |
| INSERT | straight up 45 mm along +z_M, then depth check (axial ≤ 1 mm) | joint tracking (blocked = lug on lip → back down, re-align, retry) |
| ROTATE_TO_LOCK | 45° arc about the group-head axis (9 waypoints) | joint tracking |
| VERIFY_INSTALLATION | camera: bayonet state = locked; **release test in place**: fingers open around the handle (hand does not move) → camera: still locked, i.e. held by the bayonet alone → fingers close again (`~/install`: release, back off, check from the ready pose, done) | camera |
| REGRASP | (`~/remove`, or if closing again after the release test failed) grasp the handle at the machine (measured pose) | finger |
| RESEAT | the released part hangs tilted / off-centre in the clearances: servo it back to the exact locked pose (radial ≤ 1.2 mm, tilt ≤ 1.5°) | camera |
| UNLOCK | −45° arc; blocked → back to locked, RESEAT, retry once | joint tracking |
| REMOVE | down 45 mm, out to staging | joint tracking, finger, camera (moves with hand) |
| RETURN | OMPL above the (levelled) pick pose, servo, descend to 3 cm, fine servo, lower into the stand | camera, joint tracking |
| RELEASE | open, retreat, ready; camera: portafilter at the pick pose (≤ 8 mm) | camera |
| RECOVER | never drops a held part: unlock / extract if in the machine, put back, park | – |

Contact inside the group head (mm clearances) is allowed in planning only between the held
portafilter and the mount object (Allowed Collision Matrix, set/reset by the task); the robot
itself stays collision-checked, and real contact is detected by the joint-tracking check.

## 4. Running

```bash
# complete application (Gazebo GUI, RViz with camera, debug image and task frames, y/N prompt)
ros2 launch openarm_sorting_bringup coffee_portafilter.launch.py
# headless, starts by itself
ros2 launch openarm_sorting_bringup coffee_portafilter.launch.py gz_gui:=false rviz:=false auto_start:=true
# no prompt; call services yourself
ros2 launch openarm_sorting_bringup coffee_portafilter.launch.py prompt:=false
ros2 service call /portafilter_task/plan_check std_srvs/srv/Trigger   # nothing moves
ros2 service call /portafilter_task/run std_srvs/srv/Trigger          # install + remove
ros2 service call /portafilter_task/install std_srvs/srv/Trigger      # leaves it locked
ros2 service call /portafilter_task/remove std_srvs/srv/Trigger
ros2 topic echo /portafilter_task/status
# ground truth (Gazebo only)
ros2 run visual_manipulation_gazebo check_portafilter --compare-perception
# alternatives
ros2 launch openarm_sorting_bringup coffee_portafilter.launch.py grasp_assist:=false        # pure friction grasp
ros2 launch openarm_sorting_bringup coffee_portafilter.launch.py \
    perception_params:=$(ros2 pkg prefix openarm_sorting_bringup)/share/openarm_sorting_bringup/config/coffee/perception_rgb_only.yaml
# subsystems separately
ros2 launch openarm_sorting_bringup simulation.launch.py world:=$(ros2 pkg prefix openarm_sorting_bringup)/share/openarm_sorting_bringup/worlds/openarm_coffee_world.sdf grasp_assist_child_model:=portafilter
ros2 launch openarm_sorting_bringup moveit.launch.py
ros2 launch openarm_sorting_bringup coffee_perception.launch.py
ros2 launch openarm_sorting_bringup coffee_task.launch.py prompt:=false
```

Launch arguments of `coffee_portafilter.launch.py`: `gz_gui`, `rviz`, `perception`, `task`,
`prompt`, `auto_start`, `grasp_assist`, `perception_output`, `world`, `geometry_file`,
`perception_params`, `task_params`, `nvidia_offload`, `controllers_file`, `controllers_timeout`.

Regenerating the scene after a dimension change:
`python3 src/openarm_sorting_bringup/scripts/generate_coffee_models.py`, then rebuild
(`colcon build --symlink-install`; if files were removed, delete `build/` + `install/` of
`openarm_sorting_bringup` first). `test_coffee_scene.py` checks that models, world, geometry
file and the ground-truth tool agree.

## 5. Validation

All numbers below were measured in this workspace (Ubuntu 24.04, ROS 2 Jazzy, Gazebo
Harmonic 8.15, bullet-featherstone, headless rendering, RTX 3070 Laptop) on 2026-11-24.

### 5.1 Build and unit tests

`colcon build --symlink-install`: 16 packages. `colcon test` over the project packages:
**83 tests, 0 failures** (42 pre-existing + 41 new: core math / filter / grasp / bayonet / PBVS /
state machine, ArUco pose on synthetic renders, scene shapes, task logic, coffee scene
consistency between models, world, geometry file and ground-truth tool).

### 5.2 Perception accuracy (Gazebo ground truth, 640 × 480 camera, 90° HFOV)

| Marker (distance, view angle) | RGB only, `subpix` corners | RGB only, `apriltag` corners | RGB-D refined (`apriltag`) |
|---|---|---|---|
| portafilter, 40 mm (≈ 0.55 m, 44–51°, 26–29 px) | 26.6 mm / 8.5° | 4.1 mm / 0.9° | **0.3 mm / 0.05°** |
| machine mount, 45 mm (≈ 0.45 m, 16°, 42 px) | 6.6 mm / 1.1° | 6.0 mm / 0.5° | **0.5 mm / 0.06°** |
| portafilter held in the hand (tracker output) | – | – | 0.4–0.8 mm / 0.3–0.5° |

Findings: the corner-refinement method dominates RGB-only accuracy (AprilTag-style refinement
is now the default); RGB-only range has a ≈ 1 % bias on these small rendered markers; a
fronto-parallel marker has a several-degree tilt ambiguity that the IPPE ambiguity ratio does
not flag (unit test documents it) – depth refinement removes it.

### Comparison of the alternatives

| | Recommended (default) | Alternative |
|---|---|---|
| Perception | RGB-D refined, AprilTag corners: ≈ 0.3–0.8 mm, 5/5 + 2/2 + 1/1 task successes | RGB-only: 4–6 mm, 0/2 – needs larger markers or a higher-resolution camera for a 2.5 mm clearance (works architecturally, same code) |
| Corner refinement | `apriltag` | `subpix` (OpenCV default): 4–6× worse here |
| Grasp model in Gazebo | grasp assist (weld while stalled on the grip) | pure friction (μ 3): creep 0.06°/s, 0/2 tasks |
| Release test | in place (fingers open, hand stays) | release + back off + re-grasp: 2/4 (re-grasp of a freely pivoting part) |
| Servo | command-based PBVS, 2 stages + depth check + re-seat | measured-TCP PBVS: did not converge under arm sag |
| Bayonet gaps | 1.5 mm lug/lip, 2.5 mm rim/screen | 0.8 / 1.5 mm: lugs bind while turning |


### 5.4 Development history (what failed and what fixed it)

| Observation (measured) | Cause | Fix |
|---|---|---|
| both markers decoded as id 21 | Gazebo caches textures by file name | unique texture names (+ unit test) |
| fingers stopped at 0.29–0.36 rad on a 32 mm grip | fingertips hit the tag plate / dock saddles; TCP too high | grasp band x 0.145–0.157 m, TCP 6 mm below the grip centre line, saddles removed (grasp sweep with a debug camera) |
| portafilter rotated in the grasp 0.35°/s while holding still, up to 8° / 33 mm in a lift | bullet-featherstone box contacts creep under the cantilevered 0.4 kg load | grip μ 3 (→ 0.06°/s), then the optional Gazebo grasp assist (§6) |
| servo did not converge (errors jumping 2–18 mm) | loaded-arm sag 0.015–0.022 rad; corrections applied to the measured TCP have no integral action | corrections applied to the **commanded** TCP |
| Cartesian moves inside the group head: fraction 0 | planning scene attached the part at its grasp-time pose; mm clearances | re-attach at every in-hand measurement; contact allowed only between the held part and the mount (ACM) |
| insertion blocked, part jammed 7.7° tilted | droop in the hand | two-stage servo (staging + pre-insert) with tilt correction, depth check after insertion |
| unlock after re-grasp blocked / handle twisted out (2 of 4 runs) | the released part hangs ~6° tilted; grasping a freely pivoting part | release test **in place** (fingers open around the handle, hand does not move), RESEAT servo before turning, unlock retry |
| locked part classified "out" → attempted to grasp it as if in the stand | classifier tolerance tighter than the mechanical clearances; "out" was a catch-all | states locked / inserted / partially_rotated / **misaligned** / out; only "out" may be picked |
| placements tilting more each run (5° → 11°) | rigidly held basket cannot self-centre; place pose = previous (tilted) pick pose | levelled place pose, conical lead-in, second fine servo 3 cm above the stand |
| lift reported "blocked" at 0.031 rad | tolerance from the 50 g cube task | 0.045 rad (sag ≤ 0.031, real contact 0.15–0.22) |
| tighter bayonet gaps (0.8 / 1.5 mm) to reduce the hanging tilt | lugs bind during the turn (part left at −22°) | reverted to 1.5 / 2.5 mm |


## 6. Simulation-specific decisions and limitations

* **Grasp assist (Gazebo only, default on).** bullet-featherstone (the only Gazebo Harmonic
  engine that enforces the OpenArm finger mimic joint) lets a 0.4 kg part held 12 cm from its
  centre of mass creep in a pinch grip. `grasp_assist` welds the part to the hand *only* while
  the fingers are stalled closed on the grip and releases it when they open; the task code does
  not know about it and still verifies every grasp. Without it (`grasp_assist:=false`) see
  §5.3. On the real robot the rubber pads provide this friction; validate the handle grasp
  (and the finger window) on hardware first.
* **Simplified bayonet.** Flat lip, no ramps, no compressible gasket: a released locked
  portafilter hangs 5–6° tilted within the clearances (a real group head clamps it). The task
  handles it (RESEAT), but the hanging tilt is a modelling simplification.
* **Removal after a restart (`~/remove`)** has to approach and grasp a freely hanging part; in
  the full `~/run` this is avoided by the in-place release test. See §5.3 for the measured
  install-remove result.
* **Gripper window** (0.10–0.22 rad) and the grasp band on the handle were measured in
  simulation for this gripper / handle; they are configuration and must be re-measured on the
  real robot.
* **Camera coverage.** One fixed camera; the hand hides the portafilter tag at the pre-grasp
  pose, therefore measurements are taken from the ready pose before grasping. No occlusion
  handling beyond that (no second camera, no wrist camera).
* **Speed.** 66–70 s per full cycle with conservative velocity scaling (0.2 / 0.1 holding /
  0.08 inside the machine).
* **Placement heading** in the stand is not keyed: heading errors up to ~5° remain (the next
  pick measures the actual pose anyway).
* **Path orientation constraints** for the transport are available in `MoveItClient` but not
  enabled (OMPL constrained planning is slow); the portafilter stays roughly level because
  start and goal are level.
* **Legacy cup-sorting demo:** its robot description and assets are byte-identical to the
  original; its end-to-end test showed a cube slipping out of the gripper during transport
  in one run (the same bullet-featherstone grasp physics) – see §5.3.
* **Not tested:** the Gazebo GUI and RViz windows were not visually inspected in this
  session (all runs headless); MuJoCo and the real robot are out of scope of this stage.
